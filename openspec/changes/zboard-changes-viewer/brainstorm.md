# Brainstorm: zboard-changes-viewer

> Brainstorming for this change was conducted interactively with the user in the
> parent Claude Code session (Superpowers brainstorming flow: context exploration,
> one question at a time, approach comparison, section-by-section approval).
> This file records the outcome of that session; every decision below was
> explicitly approved by the user, in the order listed.

## Design Summary

zboard v1 (merged) is a Claude Code mod that runs each task of an OpenSpec change
through research → plan → tdd → code → review (→ refactor loop) on a kanban board,
with subagents, mechanical gates, scoped `ptest` runs, per-task commits and
verified `tasks.md` flips. It starts from an already-written change and ends when
the last task is done.

This change adds the missing ends of the lifecycle as a **plan layer** inside the
same mod: a changes viewer that lists every OpenSpec change, creates new ones
(schema `superpowers-bridge`), drafts each artifact with a read-only agent,
explains a change with free structural diagrams and cached agent explanations,
iterates on artifacts through user-approved per-file diffs, gates `▶ Run` on a
free readiness checklist, hands execution to the unchanged v1 board, verifies the
finished change with a spec judge, resolves findings, and archives.

Invariants that came out of the session:

- Agents never write files. zboard alone writes, and only an accepted diff is
  written; nothing is written without user approval.
- The OpenSpec CLI (`status --json`, `instructions --json`) decides artifact order
  and completion; nothing is hardcoded to one schema.
- The judge never invents a pass: invalid output or missing evidence is
  `no_evidence`.
- The plan layer reuses v1's `Io` port, event-log pattern, Engram mirror, agent
  spawn with three-level model/effort config, panes and engine rules
  (composition root in `hooks/register.tsx`, literal matchers, atoms declared
  there, one unmatched hook per event).

## Q&A Decisions (interactive session)

| # | Question | Decision |
|---|----------|----------|
| 1 | How should a change be explained? | Hybrid: render the existing artifacts plus free structural diagrams computed from `tasks.md`; a detailed explanation with conceptual diagrams is generated by an agent only on "Explain" and cached by the change fingerprint (hash of its artifacts) until the change changes. |
| 2 | How does the user iterate on a plan? | User comment → agent proposes per-file diffs → Accept / Reject / Ask another version. zboard writes the accepted diff (agents never write), validates with `openspec validate`, and commits a plan revision `docs(<change>): <artifact> rev N` (conventional, no AI attribution). Nothing is written without approval. |
| 3 | What gates `▶ Run`? | A free automatic readiness checklist: `openspec validate --strict` passes; every requirement has ≥1 scenario; every task maps to ≥1 requirement; no dependency cycles; task size sane; acceptance criteria present. Optional "Critique" runs an opus critic whose findings can be turned into comments (→ iteration). |
| 4 | Can the viewer create changes? | Yes, with schema `superpowers-bridge` (`openspec new change <id> --schema superpowers-bridge`). Each artifact, in the order `openspec status --json` reports (never hardcoded, so other schemas work), is drafted by an agent from `openspec instructions <artifact> --json` plus accepted dependencies, and approved via diff. The plan step shows a cost forecast first and is generated per task group (one diff per group). |
| 5 | How does the brainstorm step work in a pane? | In-pane Q&A: the agent returns ONE question with options and a why; the user answers with an option button or free text; the agent is relaunched with the accumulated turns until it returns done; then `brainstorm.md` enters as a diff proposal. Cap: 15 rounds. |
| 6 | How does a change close? | After all board tasks are done → verify: `zboard:judge` (opus/high, read-only + scoped ptest) checks each requirement/scenario against code and tests with verdicts `true` / `false` / `no_evidence` / `ambiguous` / `contradiction` (with main specs), citing `path:line` and ptest evidence; `verify.md` is written via diff; archive (`openspec archive <change> --yes --json`, consolidating deltas into `openspec/specs`) is enabled only when every premise is true or explicitly accepted and the tasks linked to findings are done. |
| 7 | How are judge findings resolved? | Per finding, chosen by the user: false premise → "fix code" (adds a task to `tasks.md` via diff; runs on the board) or "adjust spec" (spec diff); no evidence → "add test" (TDD task) or "accept" (recorded in `verify.md`). After resolutions the judge re-runs only on affected items. |
| 8 | Which architecture? | Approach A: extend zboard with a plan layer reusing `Io`, the event log, Engram, agent spawn with model/effort config, and panes. |

Design sections approved afterwards, one at a time: (1) architecture and
lifecycle, (2) data model and events, (3) agents and flows, (4) UI — including a
correction adopted by the user: structural diagrams are drawn by zboard as SVG
(desktop) and ASCII (terminal), and Mermaid is rendered through `mmdc` only when
installed — and (5) testing. They form the core of `design.md`.

## Alternatives Considered

### Approach A: Plan layer inside zboard (chosen)
- **How**: New `hooks/plan/*` pure domain (lifecycle state machine, own event log
  and fold), `hooks/adapters/{openspec-cli,artifacts,prompts-plan}.ts`, a
  `plan-runner` runtime and new panes, all wired through `hooks/register.tsx` and
  the existing `Io` port.
- **Pros**: Reuses proven infrastructure (Io port, event-sourced projection,
  Engram mirror, agent registration and model/effort config, pane rendering,
  in-memory test world); one install; `▶ Run` hands off to the v1 board with no
  glue; one place that enforces "only zboard writes".
- **Cons**: Grows the composition root (`register.tsx`) and the mod's surface;
  the engine's "one unmatched hook per event" rule forces careful merging into
  existing hooks.

### Approach B: Separate mod for the viewer
- **How**: A second plugin (`zplan`) with its own panes and agents that talks to
  zboard only through `/zboard run` and the board read tools.
- **Pros**: Clean separation; v1 untouched.
- **Cons**: `$` never crosses a plugin, so Io, event log, Engram mirror and agent
  config would be duplicated; two installs; coordination through commands only.
- **Why not chosen**: Duplicates most of v1's infrastructure for no user-visible
  gain, and two mods cannot share state atoms.

### Approach C: Main-session-only workflow
- **How**: Keep the viewer as read-only panes and let the main Claude session
  author, iterate and verify through prompts and skills.
- **Pros**: Smallest code change.
- **Cons**: Approval, validation, readiness and "never invent a pass" would live
  in the model's context, unenforced; drafts could be written without approval;
  nothing deterministic to test.
- **Why not chosen**: Loses the mechanical guarantees that motivated zboard v1.

## Agreed Approach

Approach A. The plan layer is a second event-sourced domain beside the board
domain: a pure lifecycle state machine
(draft → authoring → ready → executing → verifying → retrospective → archiving →
archived), its own append-only log under `$.state` key `zboard.plan`, a pure fold
into a `PlanBoard`, and a `plan-runner` that executes actions through the
existing `Io`. Read-only `zboard:*` plan agents (brainstormer, drafter, explainer,
critic, judge) return JSON; zboard turns their output into diff proposals,
readiness checks and findings, and writes only what the user accepts. `▶ Run`
calls the existing `/zboard run <change>` path unchanged.

## Key Decisions

- Agents are read-only and hidden from the model (`agent.offer`); zboard is the
  only writer.
- One pending diff proposal per change; one active plan agent per change.
- A pending proposal becomes stale when its file changes on disk; stale
  proposals are never applied (regenerate instead).
- Applying re-reads the file and compares it with the proposal's `before`.
- If `openspec validate` fails after an accepted write, zboard restores `before`
  and creates a correction proposal.
- Explanations are cached by the change fingerprint; readiness is recomputed on
  every fingerprint change.
- Structural diagrams are computed by zboard (SVG on desktop, ASCII on terminal);
  conceptual Mermaid diagrams render through `mmdc` only when installed,
  otherwise as a Code block with an install hint (the sandbox cannot run the
  Mermaid JS library).
- Archive requires a passed verify run and every finding-linked task done.
- Engram topic `zplan/<project>/<change>` mirrors Q&A turns, revisions and
  findings.
- Non-goals: web UI, multi-user/team sync, editing code from the viewer, running
  the board pipeline differently.
